# 設計メモ

使い方は README に、なぜそうしたかをここに書く。

## ビュー

- `natural_block` を再エクスポートする。ビルダやハンドラはその型で書くので、
  import 1つで足りる。
- 解析はソースごとに1回。木は `BuildContext` に頼らないので、祖先が作り直されても
  使い回し、`source` が変わったときだけ解析し直す。
- 材料が変わらなければ、描いた木と同じウィジェットを返す。Flutter はウィジェットが
  変わらない子を飛ばすので、文書全体の作り直しが省ける。50 段落の文書で、祖先の
  作り直しが 12.2ms から 7.0ms になった。
- `customs` と `builders` は `@mustBeConst`。build のたびに書いたリストは毎回すべての
  行を描き直してタップを失い、アプリの状態を読むハンドラは最初の値のまま変わら
  ない。注意書きで覚えてもらうより、書いた場所で防ぐ。`NaturalBlockScope` を手で
  作れないのも同じ理由。

## 行

- `Text.rich` で描く。`RichText` を直接作ると選択に加わらず、`SelectionArea` で
  包んでも何も起きない。
- 行の span は材料が変わるまで作り直さない。速さではなく正しさのためで、押して
  いる最中に認識器を取り替えると、タップがエラーもなく消える。`onTap` を直接呼ぶ
  テストではこれを見つけられない。
- 行のすべての run は、周りの書式にテーマの `base` を重ねた1つの式から始める。
  根の書式と `:+` の基準、raw の run の書式を別々に計算すると、`base` が大きさを
  決めるテーマで、`:+` が隣の文字より小さく描かれたり、raw の run だけ古い大きさの
  まま残ったりする。

## レイアウト

- 始端以外のブロックは、幅いっぱいの箱ではなく `Align` で包む。幅に上限がない
  所で、寄せの記号を足しただけで文書が描けなくなることがないように。raw の箱を
  伸ばさないのも同じ理由。
- 行はセルに幅を均等に分ける。行をまたいで列が揃い、`左^^右` の `右` が右端に
  寄る。幅に上限がない所では分けられないので、セルを中身の幅に縮める。列は
  揃わず寄せも効かないが、描けないよりはよい。
- ノードを受け取るのは、子より多くをノードから読むビューだけ。`RowNodeView` と
  `ColumnNodeView` は置き方だけを決めるのでウィジェットを受け取り、自由に
  組み合わせられる。
- 短い行を揃えることと、セルの寄せを列の寄せと突き合わせることは `TableNodeView`
  が行う。木は書かれたことだけを記録するので、描く側の仕事になる。
- 表の枠線は既定で外枠も引く。表は始まりと終わりを宣言する唯一の構文なので、
  枠はソースが言っていることを表す。

## テーマ

- テーマを渡さなければ `fromContext` を使い、明るいテーマでも暗いテーマでも
  そのまま読める。`baseFontSize` は `textTheme.bodyMedium` から取り、アプリの
  普通の文字と同じ大きさにする。`:+` 1段の値はそこからは取れない。Material の
  大きさは 12、14、16、22、24、28、32、36、45、57 と段が均等でないからだ。
- 縞は `fromColorScheme` でだけ付けられる。縞は明るいテーマでは背景より暗く、
  暗いテーマでは明るくなければならず、1つの定数では両方に合わない。raw の箱の
  色も同じ理由でそこで決める。
- 「なし」は null ではなく値で書く（`const TableBorder()`、`const BoxDecoration()`）。
  だから `copyWith` は、省いた引数をすべて「そのまま」と扱える。`tableStripe`
  だけは null を許す。`Color` に「なし」はなく、透明でも塗りになるから。
- `styleFor` は、ソースが言ったことから描く書式への対応のすべてで、テーマに置く。
  自前のビルダがその順番を作り直さずに済む。
- `==` と `hashCode` は項目を並べたリスト1つを読む。項目を2か所に書くと食い違い、
  ビューが描き直しを決める比較が狂う。`NaturalBlockBuilders` も同じ。
- コードは等幅にする。正確さがすべての区間では、字下げや `l` と `1` の違いも
  中身だからだ。横スクロールは既定でオフ。折り返しはコードには誤りだが、オンに
  すると呼び出し側のレイアウトにスクロールビューが入る。

## ビルダ

- ノードの種類ごとにビルダを1つ持つ。ノードの型は sealed なので組は閉じていて、
  ビルダは正確な型で受け取り、違う種類用に書いたビルダはコンパイルできない。
- 既定のビルダは公開し、自前のビルダから委ねられるようにする。
- 文書、表の行、run にはビルダがない。文書はビューが、表の行は表が（`Table` の
  子は `TableRow` でなければならない）、run は行が `InlineSpan` として描く。
  `buildLayouts` と `buildContents` はこれらの型を受け取らないので、渡すと
  コンパイルエラーになる。
- ビルダは `BuildContext` を受け取らない。ビルダが何を読んだかは木に残らない
  ので、受け取れば周りが変わるたびに文書全体を描き直すしかない。周りを読む
  ときは `Builder` を返せば、その行だけが描き直される。
## カスタムの run

- カスタムの run をリンクとは呼ばない。パーサはカスタムであることだけを記録し、
  押したときの意味はアプリが決める。ここでは文字を一切解釈せず、
  `url_launcher` にも依存しない。
- `customs` の既定は空。押せる文字も画像も、アプリが選んで入れる。ハンドラが
  なくても書式は付くが、スクリーンリーダーに操作できると伝えるのは、何かが
  つながっているときだけ。そうでなければ守られない約束になる。
- ハンドラには材料を `CustomRun` 1つで渡す。伝えることを増やすときは項目を
  足すだけで、書かれたハンドラは壊れない。レコードではなくクラスにしたのは、
  レコードは形がそのまま型で、項目を足すとリテラルやパターンが壊れるから。
- ハンドラは span そのものを返す。説明ではなく span なので、折り返す
  `TextSpan`、`children:` 付きの `TextSpan`、`WidgetSpan`、タップ以外の
  認識器まで、Flutter でできることがそのまま使える。
- `dispose` は省略できない。解放するものがなければ `() {}` と書く。返された span
  は誰も調べないので、対応する `dispose` がない認識器は黙ってリークする。
  デバッグ時に span から認識器を探す検査では、ストリームの購読やコントローラ
  のような認識器以外のものは見つけられないが、この枠ならそれらも解放できる。
- `tappableText` は公開 API だけで書いてあり、自前のハンドラの手本になる。
- `widgetRun` の寄せの既定は、`WidgetSpan` の `bottom` ではなく `middle`。14 の
  文字の横に 20 の箱を置くと、文字の中心は `middle` で箱と同じ 10、`bottom` では
  13 になり、文字が下に垂れて見える。行の高さが最も小さく済む寄せ（`top`、
  `bottom`、`middle`）のうち、中心が揃うのは `middle` だけ。
- ハンドラは `BuildContext` を受け取らない。行は材料が変わるまで span を持つので、
  描くときに読んだ値は更新されない。周りが変わるたびに span を捨てると、押して
  いる最中の認識器を取り替えてしまう。周りを読むときは `widgetRun(Builder(...))`
  にする。
- タップの意味は、run を描いたハンドラが決める。だからビューに `onTap` はない。
  `tappableText` は `CustomRun.withContext` を通じて、タップした時点の行の
  `BuildContext` で `onTap` を呼ぶ。ハンドラはトップレベル関数のまま（リストは
  `const` のまま）で、そのときの状態に答えられる。描いている最中に
  `withContext` を呼ぶと、同じ理由で assert で止まる。

## 画像

- 画像の構文はない。画像は `image(<url>)` を中身とするカスタムの run なので、
  画像を知らない実装でも読める文字が出る。`img` は別名として受け付けず、空白も
  削らない。描かれないときに読み手が見る文字こそが慣習の要点で、綴りが2つ
  あれば、それが防ぎたい方言になる。`image( a.png )` は文字のまま見えるので、
  間違いは間違えた場所に現れる。
- 参照実装を同梱する。解釈を断っても方言は防げず、どのアプリも自分の綴りを
  作ることになる。
- `NaturalBlockImages.network` は入れるまで無効。リモートの画像を描くことは、
  文書を表示しただけで第三者に要求を送ることで、受け手ごとの印を持つ URL なら
  既読の通知になる。パッケージには見分けられないので、アプリが決める。
  メールのクライアントがリモートの画像を既定で止めるのと同じ。
- `NaturalBlockImages.local` は、設定ではなく別のハンドラ。リモートは開いたことを
  第三者に伝え、ローカルは読み手のファイルを他人の文章の下に映し、描けたか
  どうかでパスの有無を探らせる。別の判断なので、別に入れる。web では
  `dart:io` がないので、ローカルのパスは辞退する。
- `urlOf` ではなく `sourceOf`。ローカルの中身はパスで、URL ではない。`kindOf` が
  あるのは、`Uri.parse` が `C:\Users\a.png` をスキーム `c` の URI と読み、
  「スキームがあれば URL」では Windows のパスをすべて取り違えるから。
